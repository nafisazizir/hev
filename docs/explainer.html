How Hev works, and what it changes from kev

A walk from "what goes in" to "what comes out", drawn at the level of individual tokens. No prior machine learning knowledge assumed. Every figure shows a mechanism, and the two attention grids are computed on this page from the same rule the code uses.

1. The job: typed questions in, probabilities out

A normal language model writes text one word at a time. Kev, Hev and Jev do not write anything. They read a piece of text (the state) and a set of typed questions about it, and return a probability for every allowed answer. Software can use those numbers directly: route a ticket, gate a workflow, rank candidates.

Three question types exist, and all three are the same operation underneath: score a list of options and turn the scores into probabilities.

2. The whole pipeline in one picture

Before the details, here is the map. A request travels down the left column. The backbone is one stage in the middle of it, not the start: packing and the mask come before the backbone because they decide what the backbone is allowed to read. The right side zooms into one of the 28 layers to show where the mask, the position ids and the LoRA adapters plug in. Stages with a teal bar are the ones where Hev differs from kev; every other stage is identical.

So your guess of "backbone, pack, mask, readout" has the right parts. The actual order is pack, mask, backbone, readout, because the mask is an input to every attention step inside the backbone rather than something applied afterwards.

3. Tokens and vectors

A model cannot read letters. Text is first cut into tokens, small chunks of a few characters each, and each token is looked up in a table to get a list of numbers called a vector. For Qwen3-0.6B that list has 1,024 numbers. Everything that follows is arithmetic on those lists.

A transformer is a stack of layers, 28 in this model. Each layer updates every token's vector by letting it read from other tokens' vectors. After the last layer, each token's vector is a summary of that token in context. Which context it got to read is decided by the attention mask, which is the whole story of Hev.

4. Attention and the mask

Attention is the mechanism by which a token reads others. For each token (call it the query), the layer looks at every other token (the keys), scores how relevant each is, and blends their vectors into the query's vector in proportion to those scores.

The mask is a grid that says which (query, key) pairs are allowed at all. A forbidden pair is set to minus infinity before the scores are normalised, so it contributes exactly nothing. Ordinary language models use a causal mask: a token may read anything before it and nothing after it. That is the triangle below.

5. Packing: one sequence for the state and every question

Both models put the state and all the questions into one sequence, so the state is processed once no matter how many questions there are. Five rarely used special tokens act as delimiters. They cannot be produced from user text, so a hostile ticket cannot forge an option boundary.

Here is a state and one question with three options, packed the kev way and the Hev way. The tokens are identical. The only difference is where the decide token sits.

6. The mask, kev versus Hev

Now the central figure. Both grids start from the causal triangle and remove cells. Kev's rule: a token may read the state, or anything earlier in its own question. Hev's rule adds one more clause: an option may read its own question's instruction and itself, but never a sibling option.

Look at the rows for option 2 and option 3. In kev they reach back into option 1's columns. In Hev those cells are gone. That handful of cells is the entire architectural difference.

"kev" here means the revision Hev forked from, where this was the only mask rule. kev has since added an option_isolation switch of its own that removes the same cells, so the rule on the right is no longer Hev's alone — see section 12. What differs is that in Hev it is the only mask there is, paired with shared option positions and a readout that cannot see an index, rather than a flag that can be turned off.

kev:  allow(i, j) = j ≤ i and ( seg[j] == state  or  seg[j] == seg[i] )

Hev:  allow(i, j) = j ≤ i and ( seg[j] == state
                             or (seg[j] == seg[i] and sub[j] == instruction)
                             or (seg[j] == seg[i] and sub[j] == sub[i]) )

seg = which question a token belongs to (0 for the state)
sub = which option within that question (0 for the instruction)

7. Where order sensitivity comes from, and why Hev cannot have it

Ask a simple question: at the end of the network, what does option 3's vector depend on? Trace the allowed reads through all 28 layers.

The trade being made. Kev's option 3 could compare itself to options 1 and 2 while reading them, deep inside the network. Hev's option 3 is read alone. Comparison now has to happen later, in the readout (section 9). Whether that costs accuracy is exactly what the first experiment measures. In retrieval systems this same trade is called cross-encoder versus bi-encoder.

8. Positions: every option starts at the same place

Attention has no built-in sense of order, so transformers stamp each token with a position number. If options 1, 2 and 3 sat at positions 10, 13 and 16, their vectors would differ by position alone, even with the mask fixed. So Hev restarts the position counter for every option at the same value: the position right after the instruction.

9. The readout: turning vectors into probabilities

After the backbone, each question has one decide vector and K option vectors (the vector at each option's closing delimiter). A small extra network, the readout head, turns them into K scores. A softmax turns the scores into probabilities. Hev has two heads to compare.

10. Ordered levels: where order is meaning, not noise

For a score question the levels are ordered on purpose: calm, frustrated, very angry. If Hev were perfectly order-blind there, it could not know that "frustrated" sits between the other two. So for score questions only, a learned level embedding (one vector per position index) is added to each option vector at the readout. It starts at all zeros, so a fresh model is blind everywhere and learns to use order only where the labels reward it. The backbone stays untouched.

11. Training: what is learned, and from what

The base model, Qwen3-0.6B-Base, already knows English. It is not retrained from scratch. Instead:

LoRA adapters
Small low-rank matrices bolted onto each attention and MLP projection. About 10 million trainable numbers against 600 million frozen ones. This is how the backbone learns what the delimiter tokens mean and how to summarise an option under the new mask. LoRA is the same choice kev made, rank 16.
The readout head and level embedding
Trained from scratch alongside the adapters.
The loss
Cross-entropy against the labelled correct option. This is a proper scoring rule: the best strategy under it is to report your true belief, which is why the probabilities come out calibrated rather than merely ranked. An optional extra term for score questions penalises being far from the right level, not just wrong.
The data
Kev's frozen training split, reshaped into the request format from ten public classification datasets (banking intents, news topics, reviews, entailment, and so on). The two published checkpoints used kev's decision-v2 split, 3,432 records. The later controlled retrain used kev's current decision-v4 split, 10,896 records, so that Hev and kev train on exactly the same rows. During training the options are shuffled, "none of the above" is sometimes added as right or wrong, irrelevant distractors are injected, and — on v4 — minimal pairs are built that differ only in whether the right answer is present, all so the model learns to read evidence rather than memorise wording.
Temperature
After training, one scalar is fitted on a separate calibration split to sharpen or soften every distribution. Fit there, never touched again.

12. The experiment, and what it found

The experiment ran in two stages. First on kev's decision-v2 data, where Hev and kev trained on the same rows but were scored from each other's recorded ledgers. Then, because that left training data and architecture tangled together, a controlled retrain: Hev's pointer model trained on kev's own decision-v4 split under kev's published recipe, three seeds, all scored by one evaluator against the released kev-0.6b checkpoint on identical rows. Everything below is the controlled stage, on development data. The locked test split has never been opened.

QuestionWhat happened
Was order sensitivity free to remove? Nearly, on familiar questions. All three Hev seeds scored 80.67% on the ten public decision sources against kev's 81.35% on the same 1,040 rows. Paired, that is kev ahead by 0.67 points at every seed, with every 95% interval crossing zero. The equivalence bar had been fixed in advance at 2.0 points and was missed by a hair, so the honest reading is "within a point, equivalence not demonstrated" — not parity.
What does it cost? A few points on unfamiliar questions. On the six out-of-distribution transfer sources kev led by 2.71, 5.42 and 1.46 points across the three seeds. kev measured the same direction and roughly the same size for its own isolation switch, which makes the encoding the likeliest explanation — but Hev trains in fp32 on Apple silicon and kev in bf16 on an H100, so this is not a clean attribution.
Is the order invariance real? Yes, exactly. Every distinct order of every eligible Choice question: Hev flipped 0 of 628 decision questions and 0 of 348 transfer questions at all three seeds, with the correct option's probability moving by about 1e-6 — floating-point noise, not behaviour. The released kev checkpoint flipped 43 (6.85%) and 87 (25.00%).
Are the probabilities still honest? Yes. Calibrated ECE on decision was 0.0400 / 0.0394 / 0.0280 across the Hev seeds against kev's 0.0391. The mask did not cost calibration.
Does the level embedding earn its place? Not shown. Zeroing it changes the score-question probabilities but produced no statistically supported improvement in likelihood. It stays in the checkpoint; it is not claimed as a benefit.
Was the set head needed? No. SetHead's decision gain over the simpler pointer was 0.25 points with an interval from −1.17 to +1.58, and it was lower on transfer. High-K tasks like 77-way banking intents never fell far enough to need the shortlist fallback that had been prepared for them. The pointer is the default.
Two things this drawing got wrong, now corrected. Exact order invariance is not unique to Hev: kev has since shipped its own option_isolation switch and measured a 0.0 flip rate with it too, at a cost by its own measurement of about half a point on decision and 1.7 on transfer. And flip rates are only comparable when measured the same way — checking one shuffled order instead of all six reported 1.67% where six orders reported 6.85% on the same checkpoint, so any table mixing the two protocols understates the sensitive models roughly fourfold.
What the mechanism is, then. Not an accuracy win, and not a novelty claim. It is a property available by construction rather than bought with augmentation, at no measured decision-accuracy cost once data and recipe are held equal, with an unresolved transfer cost. The isolation design also makes each option a self-contained branch, which is what the next ideas need: an extract question type where the options are spans of the state itself, and dependent questions where one question's decide vector may be read by another, giving if-then logic in a single pass.

Glossary

Token
A chunk of text, roughly a short word or word-piece, that the model treats as one unit.
Vector / hidden state
A list of numbers (1,024 here) that represents a token in context. Written h(…) in the figures.
Attention
The operation by which one token's vector reads a weighted blend of other tokens' vectors.
Mask
The grid of which token may read which. Forbidden pairs contribute nothing.
Block-causal
A causal mask with extra cells removed so that groups (blocks) of tokens cannot read each other.
Position id / RoPE
The index stamped on each token so the model can tell order. Qwen encodes it as a rotation of the vector.
Prefill vs decoding
Prefill is reading the input in one parallel pass. Decoding is writing output one token at a time. These models only prefill.
Readout head
A small network on top of the backbone that turns vectors into scores.
Logit
A raw score before softmax. Higher means more likely.
Softmax
Turns a list of scores into probabilities that sum to one.
LoRA
Low-Rank Adaptation. Train two thin matrices per weight instead of the weight itself. Cheap and swappable.
Cross-entropy
The training loss: minus log of the probability given to the correct answer.
Calibration / ECE
Whether "90% confident" is right 90% of the time. ECE measures the gap, lower is better.
Permutation invariant
Output does not change when inputs are reordered.
Permutation equivariant
Reordering inputs reorders outputs the same way, and nothing else changes. What a readout over a list must be.
Argmax flip
The top answer changes when only the option order changes. Kev's measured rate: 7%. Hev's by construction: 0.
